## Crates

| Crate | Kind | Owns |
|---|---|---|
| `dex-protocol` | lib | Wire types: request/response envelopes, the closed `ErrorCode` enum, handshake messages. Serde only. TS types via the optional `ts` feature. |
| `dex-core` | lib | The daemon: `platform/` infrastructure, `features/` slices, `router`. Embedded in the app. |
| `dex-cli` | bin `dex` + lib `dex_cli` | The CLI and hook entry point. Thin: parse, send, print. The lib exposes `client` — the pipe client — and nothing else. The three installers (`hooks`, `mcp`, `skill`) and `doctor` live here too, since what they touch is outside the daemon. |
| `dex-mcp` | bin | Stdio MCP server proxying to the daemon. Depends on `dex-cli` for `client`. |
| `app/src-tauri` | bin | The Tauri app hosting the UI and the daemon. |

| `features/activity/` | `activityStore` (one `EventList` per workspace, refreshed on the `context` topic) and `ActivityPane` — the live event stream, filterable by agent (PRD §10.4) — and `ActivityPopup`, the same stream as a dialog over whatever view is up, which is what the title-bar button opens; the pane kind remains for docking it from the CLI |

**Toasts** are raised by `app/src-tauri/src/notify.rs` with `tauri-winrt-notification`; clicking one focuses the window and emits `dex://focus-pane`.

**UI → daemon path.** The UI calls one Tauri command, `dex_request`, with the same request envelope the CLI will send over the pipe; both go through `router::dispatch`. Every `workspace.*` command returns the full `WorkspaceList`, and the frontend store replaces its snapshot with it.

## Decisions

- **Frontend tests run in node, with no DOM** (`vitest`, `app/src/**/*.test.ts` beside the source, as on the Rust side). What is worth testing here is pure — key parsing, pane geometry, the toast rules — and needing a DOM is a sign the logic should come out of the component first. That is why `paneGeometry` separates `neighborIn`, which takes boxes, from the `data-pane-id` lookup: a headless DOM would not have helped, since `getBoundingClientRect` returns zeros there and every pane would sit on top of every other.
- **TypeScript wire types:** `ts-rs`, behind `dex-protocol`'s optional `ts` feature so the crate's default dependencies stay serde-only. `cargo test -p dex-protocol --features ts` writes them to `app/src/platform/generated/`.
- **MCP implementation: hand-rolled JSON-RPC, not the `rmcp` SDK** (M6). The surface needed is four methods (`initialize`, `ping`, `tools/list`, `tools/call`); the tool list must be decided at runtime rather than by a derive macro, because outside a Dex pane it is empty; and the process starts once per Claude Code session on the machine, so avoiding an async runtime keeps that startup cheap. `rmcp` 3.4.0 was available and would have worked; revisit if the protocol surface grows.
- **The pipe client lives in `dex-cli`'s lib target**, which `dex-mcp` depends on. The repository layout fixes the crate list at four, and the alternative — a third copy of the HMAC handshake after `dex_core::platform::auth` and this one — is worse than an odd-looking dependency edge.
- **Pane kinds are checked, not stored blindly.** `pane.create` and `pane.split` take `kind` (`terminal`, `activity`, `diff` or `markdown`); anything else is refused, because a pane whose kind no renderer understands would be an empty box with no way to tell why. A non-terminal pane mounts no terminal, so no shell is spawned for it.
- **The office stores nothing.** A persona is a pure function of the agent id, so it survives restarts and is the same in every view without a table, a migration, or an owner. The cost is that the hash and the order of the name and colour lists are permanent — a test pins real values so that changing either fails loudly rather than renaming everyone. The one thing not derivable from the id alone is uniqueness: two ids can ask for the same name, so within an office the earlier arrival keeps it, and that assignment (like seating) is held in the window, not the database.
- **Nothing acts on a pane nobody can see.** With the office over the workspace, a pane shortcut brings the panes back first (`whenPanesHidden`): close, move, focus and zoom stop there; split, diff and cycle-layout then go ahead. Every "take me to that pane" — a toast, the palette, the work panel — goes through one function that switches to the terminals, and terminals cannot take keyboard focus while hidden (`suspendTerminalFocus`), or an agent spawning a pane would pull keystrokes out of a memo.
- **The map's chat reads the daemon's English.** `phrasing.ts` recognises a hire and a status change by the shape of the event's body ("<label> started an agent for: …", "<label> is <status>"). That couples the office to two format strings in the agent slice; anything it does not recognise is shown as written, so a changed format degrades to plain text rather than breaking. The proper fix, when there is a second reader, is a structured field on the event.
- **Text is typed at an agent only while Claude Code is there to read it.** A pane is Claude Code only while Claude Code runs in it; for the first seconds after a hire (the row exists before `claude` starts) and after a crash it is a shell, which runs what is typed into it. `agent.prompt` is the one way the office types at an agent, and it refuses unless the agent has a started session and is idle or working - the rule the wake-up nudge learned in 0.1.1. `AgentView.started` lets the UI say why beforehand; the daemon checks again at the moment of typing. And because "has a session" is not "is still there" - Claude Code quit with Ctrl+C, or crashed, fires no `SessionEnd` - it then looks in the process table (`platform/proctree.rs`, read through PowerShell since `unsafe` rules out Toolhelp) for a Claude Code process under the pane's shell, refuses if the shell is there and Claude Code is not, and ends the agent on the spot. Only evidence refuses: no process for the pane, an unreadable table, or a WSL pane fall back to the status rule. It runs only when the owner is about to type at an agent, not on the watchdog's timer, so an agent that has gone is noticed when someone tries to reach it or its pane exits. Clock-out's `/exit` follows the same rule.
- **Stopping a spawned agent closes its pane; an agent may stop only itself and its descendants.** Dex made the pane, so Dex removes it (`agent/stop.rs`); a pane the owner opened stays unless they ask (`close_pane`), and a workspace's last pane always stays. `agent.stop` carries the pane it came from: if an agent runs there it is the one asking, and "stop the other agents" said to a confused child cannot end the lead. The owner may stop anyone. **This is a guard against a confused agent, not a security boundary:** the pane is whatever the caller's `DEX_PANE_ID` says, and an agent that cleared it would be taken for the owner. Everything on the pipe already runs as the owner's user; telling agents from the owner for real would mean identifying the calling process, which nothing here needs yet. `graceful` asks with `/exit` first - after Escape if the agent is mid-turn - so `SessionEnd` runs, and falls back to Ctrl+C.
- **Spawned agents start with `--no-chrome`.** With Claude in Chrome on by default, every new Claude Code session connects to the browser extension, which brings claude.ai up in the owner's browser — once per agent, so a lead spawning three opened three tabs. `agents.spawn_chrome = true` leaves the flag out (it is never turned *on*), which is also the way out for a Claude Code too old to know the flag. An agent the owner starts by typing `claude` is theirs and is not touched.
- **Pane shells forget the Claude Code session Dex was started from.** `pty::forget_claude_session` removes the ten variables that mark a session, named one by one because the owner's settings (`CLAUDE_CONFIG_DIR`, `ANTHROPIC_*`) share the prefix.
- **The way out is a door, not HR.** HR is where agents are hired and nothing else. Whoever ends walks to an exit in the left wall at the end of the main corridor (`EXIT_DOOR`), turns, waves, and goes. Between one corridor and the next everyone uses the side aisle (`AISLE_X`), which runs between the break room and the first column of desks, so no route crosses either.
- **A terminal is read as the lines that were printed.** The office reads a terminal's buffer rather than serializing it, and a buffer is rows: a long line is several, broken wherever the window ended. `platform/bufferText.ts` rejoins the rows the terminal marks as continuations, untrimmed, because a wrap can fall on a space. The panel reads through it - and only the open panel's agent is read (`useScreen`); with the cards gone, nothing shows every screen at once, so nothing polls them all.
- **Overlays take their size from the window, in one cell the size of the office.** A percentage height does not resolve inside a centring grid, and a grid cell left to size itself grows to its content: with 126 lines of output the popup was pushed below the window, and a long line moved it off-centre. Both were found by measuring the box with long output, not by looking at a short fixture.
- **The office is a view, not a pane.** It was first built as a pane kind with its own cards/map toggle, because the handoff said "pane kind"; what was meant was ways of looking at a whole workspace. (The cards view was removed later, at the owner's request.) A pane of it would be a second way to do the same thing, so the daemon refuses `--kind office`.
- **The view switch never writes `config.toml`.** `[ui] view` is read-only: it says what a workspace opens as until the owner clicks the switch, and the click is remembered in `localStorage`. The file is the owner's, comments and all; Dex reading it and never rewriting it is worth more than one preference living in one place.
- **An unknown pane kind gets an explanation, never a shell.** The frontend used to mount a terminal for any kind it did not recognise, so a newer daemon would have made an older window spawn shells nobody asked for. `runsShell(kind)` is true for `terminal` only.
- **The activity log can be pruned; the digest does not care.** `context.delete_event` removes one event and `context.clear_events` removes either every event or only those of agents that have ended — "ended" decided by the agent slice (`agent::ended_in_workspace`), not by a join into its table. The log is a record for the human watching, not an audit trail, so noise from agents long gone is theirs to remove; delta cursors are sequence numbers, so gaps cost nothing. In the UI a single event goes on one click (cheap to remove, cheap to have removed by mistake) and a clear asks first, since it removes what other people can see.
- **Dex's terminal is PowerShell or a WSL distro.** One choice for the whole app, in `app_state` (`workspace/runtimes.rs`, `pane.terminal`, `dex pane terminal`, the setup panel's **Terminal**): `windows` or `wsl:<distro>`, checked against `wsl.exe --list` (Docker Desktop's own distros are left out). Every new pane opens in it - a workspace's first, a split, a spawned agent's, whoever spawns it - and so is every pane whose shell has not started. A running pane is never moved on Dex's own judgement - whether a shell is idle cannot be known (PowerShell runs most commands in its own process; `sudo` hides what it runs): after a choice `pane.terminal` lists the panes running elsewhere, each marked busy unless Dex can rule it out (`workspace/switching.rs`: nothing under the shell in Windows' process table, `proctree::bare`; in WSL, the shell the only process carrying the pane's `DEX_PANE_ID`, `wsl::pane_processes`), and the window restarts the ones the owner leaves ticked (`restartIn`). A pane's `runtime` is always where its shell runs: the app records it as each shell starts (`pane.started`), so the watchdog looks for an agent where it is. As the app starts (`router::open_panes`, once this copy owns the pipe and before the window starts any shell) every terminal pane is. A pane records the terminal its shell starts in as its `runtime` (`platform/wsl.rs`), so one already running keeps its shell when the choice changes. Two exceptions: a pane in a worktree Windows git made (its `.git` file names a `C:/` path) stays on Windows; and a chosen distro since uninstalled sends Dex back to Windows at startup. Distro names match regardless of case. Every `wsl.exe` run has a 15 s limit (10 minutes for git) and ignores `WSL_UTF8`. The pane's process is `wsl.exe -d <distro> --cd <folder>`, the distro's login shell in the pane's Windows folder as `/mnt/c/...` (given with backslashes: `wsl.exe` silently starts a forward-slash `//wsl.localhost/...` folder in `/`). **No daemon runs inside the distro:** Linux runs Windows programs directly, so an agent there uses the installed `dex.exe` over the same named pipe. What crosses is the pane's identity: `WSLENV` names `DEX_PANE_ID`, `DEX_WORKSPACE_ID`, `DEX_AGENT_ID`, `DEX_SOCKET` and `DEX_DATA_DIR`, which `wsl.exe` passes into Linux and back out to a Windows program Linux runs. A WSL agent's worktree is made by the distro's own git with `--relative-paths`: Windows git records `C:/...` links Linux git cannot follow, and checks files out with Windows line endings Linux git sees as every line changed; the relative form reads clean from both. It needs git 2.48+ on each side, checked first (`GitTooOld`), and it marks the repository's format for newer git. The process table cannot see into WSL (a WSL pane's own process is `wsl.exe`, `CannotTell`), so the watchdog and the prompt check ask the distro instead: one `/proc` scan per distro lists the `DEX_PANE_ID` of every process whose command line names Claude (`wsl::claude_panes`); a distro that does not answer ends nobody. A distro is readied by `dex wsl setup <distro>` (`dex-cli/src/commands/wsl.rs`): the distro's Claude Code reads the Linux `~/.claude`, so the hooks, the MCP registration and the skill go in again there, by the same code on the distro's files through `\\wsl.localhost\<distro>` (the hooks naming `dex.exe` by its Linux path; the MCP server registered by running the distro's own `claude` through `bash -lc 'exec "$0" "$@"'`, which gives it the login `PATH` without quoting anything), plus `~/.local/bin/dex`, a two-line script that runs `dex.exe`, since agents run `dex` by name. `dex doctor` checks a distro only once it is Dex's terminal or a Dex pane runs in it - checking starts its VM - and the setup panel offers **Set up <distro>** for each (`setup_run` takes `wsl:<distro>`, only for a distro `wsl.exe` lists). `DEX_WSL_HOME` stands in for the Linux home, for an isolated test, including the `HOME` the distro's `claude` runs with. Programs there run with the `PATH` the owner's own login shell (from the user database) sets in an interactive terminal - nvm, `~/.local/bin` - asked once, printed after a marker so a profile's greeting is skipped, then used without an interactive shell. Setup ends by running `dex --version` there and says how to fix `PATH` if it fails. Setup refuses a `~/.claude` that leads to the Windows one (and when that cannot be checked), and `dex wsl status` runs `dex --version` in the distro, proving `PATH` and interop both.
- **Windows and macOS share everything above `platform/`.** The macOS port (#36) lives in the platform layer and the app shell; no feature slice knows which it is on. The local socket is a named pipe on Windows and a Unix socket (`<data dir>/dex-<user>.sock`, mode 0600, in an owner-only data folder) on macOS. A second copy is refused by an exclusive lock on `dex-<user>.lock` beside the socket, held for the app's life; only the lock's holder may clear a stale socket left by a crash, with the same handshake on top (`platform/pipe.rs`; the CLI's twin in `dex-cli/src/paths.rs` and `client.rs`). The data folder is `%APPDATA%\Dex` or `~/Library/Application Support/Dex`, and `DEX_DATA_DIR` overrides it on both. On macOS that alone isolates an instance, since the socket is in it; on Windows the pipe is named for the user, so an isolated instance also needs a different `USERNAME`. Children die with the app through a kill-on-close job on Windows, crash or not. macOS has no such thing: closing a pane, or quitting, hangs up every process under the pane's shell and kills what is left after a grace period (`platform/pty/reap.rs`). A crash leaves only the terminal hang-up, which reaches the shell and its foreground job; background jobs and anything that detached itself can outlive it. The process check reads `ps` (`proctree::parse_ps`). A pane runs the owner's `$SHELL` as a login shell with `TERM`/`COLORTERM` and a UTF-8 `LANG` it would otherwise lack; and because an app started from the Finder has a bare `PATH`, what Dex runs itself (`git`, `dex` for setup, which runs `claude`) gets the `PATH` a login shell prints, asked for once (`platform/login_env.rs`). Toasts are Notification Center banners through `osascript` for now, credited to Script Editor, which clicking one opens (#40). CI runs every check on `windows-latest` and `macos-latest`. The Windows installer is built the same way, by `.github/workflows/windows.yml` on `windows-latest`, checked by unpacking it (`msiexec /a`) and running its `dex --version`, and attached to each published release - no longer built on the owner's machine, where Smart App Control refuses what a fresh Rust build compiles. The Mac build is `Dex.app` in an unsigned (ad hoc signed) `.dmg`, one for Apple Silicon and one for Intel, both built on an Apple Silicon runner by `.github/workflows/macos.yml` and attached to each published release. `dex` and `dex-mcp` sit beside the app in `Contents/MacOS`, built for the same target by `app/scripts/stage-macos-sidecars.mjs`; the skill is in `Contents/Resources/skills`. A pane's `PATH` starts with `Contents/MacOS`, so agents find `dex` without an installer.
- **A pane can live in a window of its own.** A second webview of the same app (`src-tauri/src/popout.rs`, label `pane-<id>`, told its pane by an init script; the command is async because a synchronous one that builds a window deadlocks on Windows). The terminal moves by a hand-off, because output is bound to the window that took it: `PtySupervisor::hold` keeps the pane's output in its `Relay` (`platform/pty/relay.rs`) and returns how many bytes the old window was sent; the old window waits until it has received them all, flushes xterm, serializes its screen and scrollback; the new window draws that and `attach`es, receiving what was held and everything after - nothing lost, nothing shown twice (tested in `relay.rs`). Docking reverses it; a pop-out that vanishes without docking (`popout-closed`) brings the pane home with the main window's last screen and a line saying so. In the main window the pane stays in the stored tree and is left out of the drawn one (`shell/visibleLayout.ts`, with each split keeping its stored path so divider drags still land). Closing the main window quits the app (`popout::quit_with_main`). The office's *their screen* for a popped-out pane shows the screen it had when it left: the main window no longer receives its output. While it is out, the main window never treats it as the focused pane (`visibleActive`): keys would go nowhere and pane shortcuts would act on it unseen. After a hand-off the terminal tells the PTY its size whether or not xterm saw it change (`resizeOnShow`), or a docked pane would keep the pop-out's width. Known: output that piles up while a hand-off waits on a slow window is subject to the usual unresponsive-display rule - past five seconds paused, it is dropped with the usual marker.
- **A pane is moved by dragging its header onto another.** `pane.move` (`workspace/pane_move.rs`) with the rule pure in `workspace/docking.rs`: dropped on an edge, the pane leaves its place - its parent split closes up, as when a pane is closed - and splits the target on that side at half; dropped in the middle, the two swap (`layout::swap_panes`). The moved pane takes focus. In the app, `shell/paneDrop.ts` decides the side from the pointer (the nearest edge within a quarter of the pane, else the middle) and when a press becomes a drag (6 px, so a click on a header still only focuses); `shell/PaneDrag.tsx` does the pointer work with window listeners and `elementFromPoint`, draws the hint, and sends one request on release. Escape cancels. A zoomed pane does not drag.
- **A spawn's pane goes beside the caller's earlier hires, not off the caller again.** Six spawns from one lead sliced the lead six times (issue #31). `agent/placement.rs`: the first child splits the caller the way it asked (`--direction`), every later one splits the newest living sibling across that direction - a strip beside or below the lead, whose pane keeps its size; `store::live_sibling_panes` says who the siblings are, with the owner's own hires (no parent) counting as one family. And a workspace arranged as a preset that grows well - main-left, main-top or tiled (`Preset::grows_well`) - is re-arranged as that preset with the new pane in it (`workspace/arrange.rs`), so a grid stays a grid; an even row or column, or a layout made by hand, is left alone and the new pane joins the strip. Moving a pane (`Alt+Shift+Arrow`) and cycling presets were already there for after the fact.
- **Labels belong to panes, and the office shows agents.** A pane the owner opened outlives its agent and keeps its label, where nobody in the office can see it; hiring with that label was refused as "already used" with no agent in sight, and read as a bug. HR's form now checks first (`labelClash`): it says what holds the label - an agent's pane, or a pane with no agent in it - and offers the next free one. The daemon's repair text says the same for the CLI and for agents.
- **The certain way for an agent to ask the owner is Claude Code's question dialog.** `AskUserQuestion` fires `PermissionRequest`, so the agent is `waiting` as it asks; `agent/reason.rs` reads the question out of the tool input (`asked you: ...`, not "permission to AskUserQuestion"), and the notification Claude Code sends a few seconds later - "Claude needs your permission" - no longer replaces a reason a dialog already gave (`keeps_its_reason`). Agents are told: the `SessionStart` digest carries one line saying how the owner hears a question, stated as a fact because the digest orients and does not instruct, and the skill says it at length. A real agent given the owner's decision to find out chose the dialog with no other prompting. Everything below is the fallback for when one does not. (The watchdog moved to `agent/watchdog.rs` to keep `commands.rs` under the file limit.)
- **An agent that ends its turn on a question is idle to Claude Code and waiting to the owner.** `Stop` carries `last_assistant_message`; `agent/asking.rs` reads how it ends (the last two sentences: a question mark, a cue such as `reply "yes"` / `tell me and`, or the grammar of a question - an auxiliary before its subject, at the start or after a question word, so "what would it be." asks and "what it would be" does not; closing pleasantries excluded) and puts `asked you: ...` in the status detail. Otherwise it puts `said: ...`, the closing paragraph: the guess has a net under it, and the office shows it: a question in a speech bubble at the agent's mouth (`AskBubble` in `Pod`), anything else as a quiet line under their desk (`lastSaid`). What was merely said stays out of the workspace log, which agents' digests are drawn from. The status stays `idle` on purpose: answering is an ordinary prompt, which `agent.prompt` refuses for a `waiting` agent because typed text would answer a dialog, and the wake-up nudge wakes only agents at their prompt (`idle`, or `unknown` - see the waking bullet). In the app, `features/agents/attention.ts` (`seenAs`, `askedYou`) is the one place that turns this into "waiting" for everything that *shows* a status - badge, sidebar dot, title-bar counts, toasts, the office pose, and whether someone may wander off - while everything that decides whether an agent may be typed at keeps using the status itself. Other agents are not told what was asked, as they are not told what a dialog is for. Known and accepted: a sentence opening "Should you want to revert, run..." has a question's grammar and is taken for one until the next prompt; and what an agent said last is shown on the floor as written, where a permission reason is deliberately stripped of arguments - it is the owner's screen, other agents are not told, and cutting an agent's prose on a guess about secrets would hide the line it exists to show. Cues match whole words, and a closing list is read item by item (both from review). Announce warns when it would reach an agent in the middle of a question of its own (`midQuestion`). Found when an agent asking for a "yes" went for a coffee; the grammar rule and the closing line came from the owner's first test of the fix, "ask me a question, but end it with a period".
- **An agent is Claude Code running in a pane; where it no longer runs, the agent is dead.** Quit with Ctrl+C, crashed or killed, Claude Code fires no `SessionEnd`, and "idle" would stand over a bare shell for ever - in the list, in the office, against the spawn limit. The watchdog (`agent/presence.rs`) asks the process table about every living, started agent each sweep and ends whoever has no Claude Code under their pane's shell. Only on evidence: no process of its own, a table that could not be read, or a pane inside WSL ends nobody. The table costs a PowerShell start, so it is not read when there is nobody to look for, and a departure is confirmed by a second look two seconds later - Claude Code replaces its own process when it updates. It is said in the workspace log like any other end ("kid is dead (Claude Code is no longer running in its pane)"), so a lead is told its child crashed. A pane Dex made for a spawned agent is closed, as `agent.stop` closes it; a pane the owner opened stays - it is their shell, and may say why - and starting `claude` there again is a new session, and a new agent. A miss costs an agent, so the test for "is Claude Code" is generous (anything under the shell whose command line names it, or the pane's own process), and a runtime whose command line cannot be read concludes nothing. The look runs last in the sweep and is never fatal to it.
- **An agent with no pane is over, whatever its status says.** `agent.pane_id` is `ON DELETE SET NULL`, so closing a pane (or losing it with a crashed session) nulled the pane and left status `idle` and `ended_at` null. Those rows counted toward the six-agent spawn limit while `agent.stop` refused them as "already ended" — the 0.1.2 report: a workspace stuck below capacity with no way out but recreating it. Three places now agree: the limit counts only agents with a pane; the watchdog sweep ends every pane-less live row (`status_detail = "pane closed"`) and announces it; and `agent.stop` on such a row ends it and succeeds, with `Stopped.pane = None`, since ending is all that stopping can mean without a pane. A spawned child whose shell never appears within the launch wait is ended too (`"never started"`), rather than left `idle` for ever.
- **A directed message to an agent at its prompt wakes it, and the watchdog wakes whoever a message caught mid-turn.** Digests reach an agent only at its next turn, and an agent sitting at its prompt has no next turn until someone gives it one - so a parent's "the requirement changed" to a finished child sat unread forever (found in the first real use of 0.1.0). `context.message_send` types a one-line prompt into the target's pane (`context/wake.rs`, via `workspace::send`, so text and Enter are separate writes) when the target is at its prompt, has **started** (has a session), and the message is newer than the last wake it was given. A message that arrives while the agent works waits for its turn to end - and then the **watchdog** wakes it (`agent/waking.rs` from `agent.sweep`, so within 15-20 s: the timer is 15 s, and the sweep reads the process table before it types), not the hook that ended the turn: Claude Code waits on its hooks, and text typed into a session that is still starting up is swallowed. That gap is what issue #58 was; the old rule also woke only for an agent's *first* unread message, so once one landed mid-turn nothing ever woke it again. The mark is the pair `context_cursor.woken_at` (newest message woken for) and `woken_idle_at` (the agent's own `status_at` then), taken with the decision inside one `Db::call`, so racing hooks and sweeps wake it once; a nudge that cannot be typed gives the mark back, so the next sweep tries again, and the sender is told `Sent { delivery }` - `woken`, `next_turn`, `waiting_on_owner` or `ended` - rather than a bare "Sent". `agent.sweep` looks for the departed *before* it wakes anyone: an agent whose Claude Code was Ctrl+C'd still looks idle, and its pane is a bare shell that would run the nudge as a command. Known and accepted: the nudge is typed wherever the owner's cursor is, so a half-typed line in that pane is submitted with it (digests are injected through hook stdout, not typed, so they never interleave); `unknown` agents are woken too, because a dropped `Stop` hook looks exactly like one, and Claude Code queues text typed at an agent that turns out to be working; an agent whose closing line was read as a question for the owner (`agent/asking.rs`, false positives and all) is never woken until the owner types at it - the message is still in its inbox and in the next digest; and the departure check is evidence-only, so where the process table cannot be read, or a distro does not answer for a WSL pane, the nudge can still be typed into a bare shell, which runs it as a command. A write that times out keeps its mark rather than giving it back: bytes may yet land, and a pane that blocks its writes would otherwise collect a nudge every sweep. The `agent` and `context` slices call each other here (`agent::waking` -> `context::take_wake`, `context.message_send` -> `agent::whereabouts`); the cycle predates this and is named rather than deepened quietly (conventions §1.2 rule 4, §7) - which is why whether an agent may be typed at is decided in one place, `agent::waits_at_its_prompt`, and asked by both.
- **Agent status changes are logged to `context_event` but excluded from delta digests.** The activity pane is how a human follows several agents, so it needs them; another agent does not, and a sibling cycling through idle and running several times a turn would spend the whole delta budget saying nothing actionable.
- **The context mirror is a projection, never authoritative.** A mirror write that fails (read-only checkout, disconnected share) logs to stderr and does not fail the command; SQLite is the source of truth.
- **Only a `PostToolBatch` delta starts the delta rate-limit clock.** A `SessionStart` full digest or a `UserPromptSubmit` delta advances the cursor but not the clock — otherwise an agent that had just oriented itself, or whose human had just typed, went silent for a minute, which is exactly the autonomous case deltas exist for.
- **PTY I/O runs on threads, not tokio tasks** (a deliberate reading of PRD §7.1's "one tokio task per PTY"). `portable-pty` readers are blocking, so reading needs a thread regardless; making the coalescer a thread too lets flow control be a plain bounded `sync_channel` — when the display falls behind, the coalescer stops pulling, the channel fills, the reader blocks, and ConPTY pauses the child. Three named threads per pane; shutdown is documented in `platform/pty.rs`.
- **PTY output reaches the UI over a per-pane Tauri Channel as raw bytes**; acknowledgements flow back through `pty_ack` in batches of 64KB or every 50ms (`app/src/platform/terminalRegistry.ts`).
- **MCP registration goes through `claude mcp add --scope user`** (`dex mcp install|uninstall|status`), never through an edit to `~/.claude.json`, which also holds the owner's login session and per-project trust. Running `claude` with an argument list means no shell expands the `${VAR:-}` placeholders at install time — the hazard the PRD warns about for PowerShell — and the install reads the registration back to prove they survived.
- **Hook installation lives in the CLI** (`dex hooks install|uninstall|status`), not in PowerShell: it edits `settings.json` with an order-preserving JSON parser, recognizes its own entries as `dex.exe … event …` exec-form commands, keeps a one-time `settings.json.dex-backup`, and writes through a temp file and rename. `scripts/install-hooks.ps1` is a thin wrapper.
- **Which state changed is announced per topic** (`workspaces`, `agents`) by `router::changes`, so the UI re-reads only what moved.
- **Production builds go through the Tauri CLI** (`npx tauri build`): a plain `cargo build` of `app/src-tauri` loads the Vite dev server URL instead of the embedded frontend. **`cargo build --workspace` counts as a plain build**, and the dev-pointing `dex-app.exe` it leaves is considered up to date by a later `tauri build`, so the app silently keeps showing "localhost refused to connect". Recover with `cargo clean -p dex-app --release`, then build through the Tauri CLI. **`--release` matters:** without it `cargo clean -p` touches only the dev profile and reports `Removed 0 files`, leaving the release binary as it was. The same applies to the icon: `tauri-build` embeds `icons/icon.ico` without a `rerun-if-changed` for it, so a new icon reaches the executable only after a release clean — which is how a rebuilt exe came out still carrying the old icon.
- **A spawned agent's row is created before its Claude Code starts**, carrying its parent and brief. `SessionStart` adopts it — by `DEX_AGENT_ID`, or by being the one row in that pane still waiting for a session. Without the second path, a child whose environment lost the variable would register a fresh agent and orphan the brief.
- **Settings are validated, not rejected.** A value Dex cannot use is replaced by its default and reported; only a TOML syntax error fails, and even then a *reload* keeps the settings already in force, because an editor saving mid-keystroke must not reconfigure the running app. The problems from the last read are kept, not just returned, so `dex config show` can answer what went wrong at startup — the app is a GUI, and a problem only logged is a problem nobody sees.
- **The installer adds four things to Tauri's MSI and runs nothing.** A WiX fragment (`app/src-tauri/wix/dex.wxs`) puts `dex.exe` and `dex-mcp.exe` beside `dex-app.exe`, ships `skills\dex-agentic\SKILL.md` beside them for `dex skill install` to copy, appends the install directory to the machine PATH, and registers Dex's AppUserModelID under HKCU (Tauri's template already stamps the same id onto the Start Menu shortcut; the toast code uses it when registered and PowerShell's otherwise). It does **not** run the hook or MCP installers: an MSI runs elevated and those write the *user's* Claude Code configuration, which is what the first-run panel is for, in the user's own session, with their click. The sidecars come from `npm run sidecars` in `beforeBuildCommand` rather than Tauri's `externalBin`, because `tauri-build` copies `externalBin` files at compile time and a plain `cargo build` or `cargo clippy` would fail whenever they had not been built yet; the fragment finds them at `$(var.SourceDir)\..\`, the one path that does not depend on where candle runs.
- **The update check tells; it never installs.** `app/src-tauri/src/update.rs` makes one GET to GitHub's releases API (startup, then every six hours, from `platform/update.ts`), compares the tag with `CARGO_PKG_VERSION` numerically — a tag it cannot parse is never "newer", or a stray tag would raise a pill nobody could dismiss — and the title bar shows a pill only when a newer, non-draft, non-prerelease version exists. Clicking opens the release page in the browser, and only a URL under Dex's own releases is ever opened. A failed check is `None`, not an error: the title bar has nothing to say about GitHub being unreachable. `[updates] check = false` turns it off.
- **First-run setup has one implementation, and it is the CLI's.** The panel runs `dex doctor --json` for its checks and `dex hooks install` / `dex mcp install` for its buttons, as subprocesses (`app/src-tauri/src/setup.rs`), so it can never disagree with what the docs tell a person to type, and the steps it can run are a closed list of three: hooks, the MCP server, and the skill. `dex skill install` copies the shipped `SKILL.md` into `%USERPROFILE%\.claude\skills\dex-agentic\`; `status` compares the two byte for byte, so after a Dex upgrade the check goes red until the owner refreshes it — a copy, not a link, so an upgrade never changes what an agent reads behind the owner's back. Its uninstall removes one named file and then the folder only if that emptied it, and refuses any folder not named `dex-agentic`; nothing in it is recursive. It offers itself when something fails and the owner has not dismissed exactly that set of failures — dismissing "MCP not registered" today does not hide "git missing" next month — and is always reachable from the palette.
- **A markdown pane's file is its `cwd`.** The `pane` table has one path column and a markdown pane points at one path, so it goes there rather than in a new column and migration; `logic::pane_kind` documents what `cwd` means per kind, and creating a markdown pane requires an existing file where every other kind requires a directory. Reading the file goes through `pane.content`, keyed by pane, not path: "read any file" is not a capability the pipe offers, and this way a file is readable over it only once someone opened a pane on it.
- **The markdown renderer builds elements, never HTML.** The parser yields a block tree and `MarkdownView` maps it to React; there is no `dangerouslySetInnerHTML` to reach. Agents write these files, so this is a boundary, not a style choice. Links do not navigate — a click in a webview would replace the app — and only `http(s)`, `mailto`, anchors and relative paths survive as links at all.
- **The palette's fuzzy scorer searches every way the query could land, not the first.** A greedy left-to-right match takes the first `s` it sees; the right match for "sr" is the `S` and `r` that start the words of "Split right". The search is memoised on (query index, text position), which is sound because the position just matched is always one behind — texts and queries are short, so this costs nothing measurable. Scores are tuned relative to each other and the tests assert orderings, never numbers.
- **Keybinding defaults live in the frontend, overrides in the config.** `[keys]` carries only what the owner changed, so the table has one owner; `buildKeymap` merges them onto the shipped bindings. An override that cannot be used leaves its action on the default rather than unbound, which would be a silent way to lose a shortcut. A binding with no modifier is refused: it would take an ordinary letter from the terminal on every keystroke, which looks like a broken keyboard rather than a setting.
- **The daemon reads pane output in exactly one place, and only when asked.** `PtySupervisor::answer_once` arms a phrase and the keys to type when it appears; `spawn` uses it for the folder-trust dialog, and nothing else uses it. The alternative — typing on a timer — would fire at a prompt that may not be there, in a directory Claude Code is already trusted in. The match is made on the output reduced to letters and digits with escape sequences removed, because a pane wraps lines mid-word and Claude Code draws dialogs inside a box, so the phrase is rarely contiguous. Dex answers it for every child, since a child never lands anywhere the owner did not already choose — the parent's folder, a registered repository, or a worktree made from one; it does not answer the settings-trust dialog, which asks whether to run the hooks a project declares.
- **`agent.spawn` announces `workspaces` itself.** It changes two things — a new pane and a new agent — and `router::changes` announces only one per command. Without that the pane never reaches the UI, so no terminal mounts, so no shell starts, so the child is never launched.

## Third-party quirks (keep these comments when refactoring)

| Where | Quirk | Handling |
|---|---|---|
| `portable-pty` 0.9.0 | Creates the pseudoconsole with `PSEUDOCONSOLE_INHERIT_CURSOR`: ConPTY first sends `ESC[6n` and renders nothing until answered. | xterm.js answers in the app; tests answer it in their drain helper. Documented in `platform/pty.rs`. |
| `portable-pty` 0.9.0 | The cloned Windows child killer returns `Err(last_os_error())` when `TerminateProcess` *succeeds* - whatever error an earlier call left on the thread, of any value, not only 0 (0.6.0 read only 0 as success, and restarting a pane in another terminal failed as "process exited with code 1") - and `Ok` when it fails, as it does for a process that has already exited. | `pty/kill.rs` reads any `Err` as success and `Ok` as `PtyError::KillFailed`, on Windows only. A restart whose kill fails still waits a second for the shell's exit (`restartIn`), which comes when the shell had ended on its own. |
| `portable-pty` 0.9.0 | Arguments containing `"` are escaped as `\"`, which `cmd.exe` does not understand. | Pass paths as separate arguments rather than quoting inside one. |
| `win32job` 2.0.3 | Dropping the `Job` closes its handle; with kill-on-close and the app assigned, that kills the app. | `main` holds the job in a binding that lives until exit. |
| Tauri 2 | Async commands run concurrently on a thread pool, so consecutive `invoke`s can complete out of order — keystrokes sent one `pty_write` each arrived reordered ("ehco"). | `terminalRegistry` keeps one write in flight per pane and batches input typed meanwhile. Apply the same pattern to any other order-sensitive command stream. |
| WebView2 / `SendKeys` | Synthetic key events often carry no scan code, so `KeyboardEvent.code` is empty. | `shell/keybindings.ts` falls back to `event.key`. |
| Claude Code 2.1.273 | `SessionEnd` fires on interactive `/exit`, but **not** when the process is killed (Ctrl+C) and **not** in print mode (`claude -p`) — measured, and consistent with the documented 1.5 s shutdown budget. An agent would otherwise sit at `running` until the watchdog noticed. | `agent.stop` ends the row itself rather than waiting for the hook, and `logic::revived` undoes that if a later hook proves the session survived. The watchdog still covers every other delivery failure. |
| Claude Code 2.1.273 | The folder-trust dialog is skipped **only** in non-interactive mode — `-p`, or when stdout is not a TTY. An interactive session in a directory it has not seen always stops there, and a spawned agent has no human to answer it. It also ignores input for 150 ms after opening, and **every ignored key restarts that window**, so typing early is worse than typing late. | `agent::spawn` arms `pty::answer_once` on the phrase "Yes, I trust this folder", waits 500 ms after it appears, then sends Down and Enter as separate writes 200 ms apart. For every child: it was first limited to worktrees Dex created, and the first real use spawned into the parent's own folder — three children stalled at the dialog. |
| Claude Code 2.1.273 | Folder trust is keyed on the git **common** directory, not the working directory: accepting it in a worktree records the *main* repository's path in `~/.claude.json`. | So the dialog appears once per repository, not once per worktree — later spawns into the same repo never see it. This is also how the answer was verified: the flag appeared for a repo that had not existed before the run. |
| `claude mcp add` 2.1.273 | `-e` is variadic, so a server name placed after the last `-e` is swallowed as another environment value and the command becomes the name — the failure reads "missing required argument 'commandOrUrl'". | `dex mcp install` passes the name before the `-e` flags. |
| `claude mcp get` 2.1.273 | Prints env values without their defaults: a stored `${DEX_PANE_ID:-}` displays as `${DEX_PANE_ID}`. Checking the read-back for the exact stored text would fail on a correct registration. | The check looks for the placeholder's presence, not its exact text. |
| Claude Code 2.1.273 TUI | Text and Enter arriving in one write are read as a paste: the Enter becomes a newline in the prompt box instead of submitting, so the prompt is never sent. Shells are unaffected. | `pane_io::send` writes the Enter separately, 50 ms behind the text (`ENTER_GAP`). Verified against a real session: 50 ms submits, one write does not. |
| `tauri-plugin-notification` 2 | Notification actions and click callbacks are mobile-only; on desktop a click does nothing the app can observe. | Toasts use `tauri-winrt-notification` directly (`on_activated`). An unpackaged dev build borrows PowerShell's AppUserModelID so Windows shows the toast at all. |
